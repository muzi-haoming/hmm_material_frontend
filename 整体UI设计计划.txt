## 二、 核心界面详细设计方案

### 1. 首页：角色感知工作台 (Workbench)

这是提升效率的灵魂。它不是一个死板的菜单，而是根据 `todo` 表生成的**行动指令集**。

* **顶部：动态统计卡片**
* **代理人 (Agent)**：显示“待我确认的合同”、“本月对账进度”。
* **厂家 (Manufacturer)**：显示“待我出库的订单”、“当前库存预警”。


* **中部：待办事项流 (`todo`)**
* 采用“即时卡片”，显示标题、紧急程度、关联单据。
* 点击直接跳转至 `todo_path` 对应的详情页。


* **底部：快捷操作**
* 根据 RLS 权限显示按钮。例如：厂家视角只显示“扫码入库”；代理人视角显示“新建采购”。



### 2. 列表页：状态驱动型过滤 (Status-Filter)

针对 `contract_order` 或 `general_purchase` 等单据，效率的关键在于**快速定位**。

* **分栏组件 (Tabs)**：`全部` | `待确认` | `已确认` | `已完成`。
* **卡片设计**：
* **左侧**：产品缩略图或厂家首字母头像。
* **中间**：单据编号 (`code`)、工地名称、总数量。
* **右侧**：利用 `is_confirmed` 字段显示彩色状态标签（确认=绿色，未确认=橙色）。


* **搜索与筛选**：支持按 `site_id` (关联角色所属工地) 或日期段过滤。

### 3. 详情页：数据一致性锁死 (Data-Lock)

这是为了配合你的 `check_bill_status_rules` 触发器，确保 UI 无法发起非法请求。

* **沉浸式状态栏**：顶部显示巨大的状态标识。
* **字段隔离渲染**：
* **编辑模式**：当 `is_confirmed = false` 时，所有输入框可选。
* **只读模式**：一旦 `is_confirmed = true`，除了 `is_completed` 开关，其余表单全部置灰禁用。


* **底部动作栏 (Action Bar)**：
* **智能按钮**：如果单据未确认，显示“确认单据”；如果已确认但未完成，显示“确认完成”及“关联发票”。
* **权限防御**：如果当前用户 `auth.uid()` 不是 `creator` 或 `modifier`，且不是 Admin，则不显示修改按钮。



### 4. 仓储：库存透视表 (Inventory)

基于 `stock` 表和 `uk_stock_manufacturer_product` 约束。

* **库存看板**：
* 按厂家聚合显示。点击厂家进入“产品明细”。
* **预警逻辑**：如果 `quantity < 0` (虽然数据库有约束，但在 UI 上可以设置安全库存阈值)，该条记录高亮红色。


* **出入库扫码器**：
* 模拟摄像头取景器。扫码后自动匹配 `product` 表中的编码。
* 联查关联单据。例如：入库时自动关联对应的 `contract_order_id`。

## 技术细节：如何实现“完美主义”的体验？

### 1. 按钮的“物理隔离”

根据你的 RLS 策略，厂家视角和代理人视角在同一个页面看到的按钮是不同的：

* **厂家**：只能看到“出库”按钮。原因：`contract_order_stock_out_insert_policy` 检查了厂家关系。
* **代理人**：只能看到“入库”按钮。原因：`contract_order_stock_in_insert_policy` 检查了工地关系。

### 2. 状态锁死逻辑

为了配合 `check_bill_status_rules` 函数，前端需实现：

```javascript
// 伪代码：提交前的终极校验
if (new_is_confirmed !== old_is_confirmed && new_is_completed !== old_is_completed) {
    showError("系统严禁同时修改[确认]与[完成]状态！");
    return;
}

```

这能有效减少无效请求，提高后端触发器的执行效率。

### 3. 库存实时感

在出库页面，实时显示 `stock` 表中的 `quantity`。由于你定义了 `uk_stock_manufacturer_product` 唯一约束，前端可以直接通过 `manufacturer_id` + `product_id` 定位到唯一库存数值，给用户提供即时参考。

## 针对你数据库设计的“伙伴式”优化建议

### 1. 处理“删除保护”的反馈

你的触发器中有非常严谨的外键检查逻辑（循环遍历 `pg_constraint`）。

* **UI 方案**：当用户尝试“取消确认”一个已有关联发票的对账单时，UI 应该直接弹窗提示：**“无法取消确认！请先移除关联的发票（发票号：XXXX）”**。这比原始的数据库错误提示更具有引导性。

### 2. 发票的安全性隔离

你的 RLS 策略规定 `invoice` 只有 `creator` 或 `admin` 才能删除，且不能存在关联关系。

* **UI 方案**：在发票管理界面，如果一张发票已经关联了对账单，直接**隐藏“删除”按钮**，从根源上避免触发数据库报错。

### 3. RLS 嵌套性能优化建议

虽然你提到数据量在“百行级别”，但财务查询通常涉及多表联查（对账单-详情-发票）。

* **UI 方案**：建议在列表页采用**懒加载**，且在查询 `statement` 时，通过 Supabase 的 `.select('*, statement_material_detail(count)')` 一次性带出明细数量，减少点击后的二次等待感。

### 1. 用户与角色工作台 (User & Identity)

**核心逻辑**：所有表均开启 RLS，仅管理员具备 `INSERT`、`UPDATE`、`DELETE` 权限。

* **物料清单管理 (`product`)**：

### 3. 关系映射矩阵 (The Permission Matrix)
